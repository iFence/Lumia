# Lumia 超大图渐进式查看设计

## 背景

Lumia 当前把普通栅格文件路径直接交给 GPUI 解码并创建单张纹理。对于
34752×11584 的图片，RGBA8 展开后约需 1.5 GiB 内存，且单边尺寸通常超过 GPU
安全纹理上限，因此即使文件本身只有 188 MB，也可能无法显示或导致进程内存剧增。

目标是在不影响普通图片快速路径的前提下，让 PNG、JPEG、WebP、BMP、TIFF、GIF
等常见格式的超大图片能够快速出现预览，并在用户放大、拖动时按需补充高清细节。

## 方案选择

采用“低清预览 + 按需高清瓦片”，而不是始终缩小或强制完整解码：

- 普通尺寸图片继续沿用 GPUI 路径加载，保持现有启动和浏览性能。
- 超大图片由官方内置进程插件处理，隔离解码器崩溃和内存峰值。
- 首先生成最长边约 2048 像素的预览，让用户尽快看到内容。
- 根据缩放级别和视口只请求当前可见的 512×512 高清瓦片，并预取一圈邻近瓦片。
- 原图尺寸始终用于缩放、状态栏和导航，预览尺寸不会替代原始尺寸语义。

## 超大图判定

读取元数据后，满足任一条件即进入 `LargeImageSession`：

- 任一边超过 8192 像素；
- `width × height × 4` 的受检计算结果超过 256 MiB；
- 图片尺寸超过应用定义的 GPU 安全纹理边界。

所有乘法、行大小和瓦片数量都使用受检运算。畸形尺寸在分配前返回资源限制错误。

## 组件与数据流

`lumia-plugin-api` 增加超大图探测、预览和批量瓦片请求/响应。请求仍只传输入路径、
矩形、缩放级别和临时输出路径；像素数据不进入 JSON。`lumia-plugin-host` 在调用前校验
能力和 `ReadInputPath`、`WriteTemporaryOutput` 权限。

新增官方 `lumia-plugin-large-image`。插件保持一个进程，在内部维护受限工作池，并按格式
选择低内存路径：PNG/BMP 逐行处理，JPEG 使用缩放解码能力，TIFF 优先使用 strip/tile，
WebP/GIF 等格式使用受控帧解码。超大动图第一版只显示首帧。不能理想随机访问的格式可
生成临时瓦片缓存，但不得在主进程完整展开原图。

应用侧 `LargeImageSession` 保存 generation、原始尺寸、预览、可见瓦片、待处理请求和取消
令牌。视口变化会计算所需瓦片集合，取消或丢弃过期 generation，并批量请求缺失瓦片。
渲染层把预览作为底图，把已就绪的高清瓦片按原图坐标覆盖在上面。

## 并发模型

插件工作池默认使用 `min(逻辑核心数 - 1, 6)` 个线程，至少给 UI 留出一个核心。并行任务
包括独立瓦片的缩放、颜色转换、编码，以及少量缓存读取。PNG 主压缩流具有顺序依赖，
主解压不强行并行；扫描行产生后再分发可并行工作。

任务优先级依次为首屏预览、可见高清瓦片、邻近预取。除线程数外，再用约 256 MiB 的
像素预算限制同时在途的缓冲区，避免多个线程各自分配大块内存。应用侧瓦片采用约
256 MiB 的 LRU 内存上限。并发数和预算作为内部常量起步，后续根据基准结果调整。

## 缓存与生命周期

磁盘缓存键由规范化路径、文件大小和修改时间组成。缓存写入先使用 `.part` 文件，完成后
原子重命名。应用退出或下次启动时清理过期和残缺缓存，并限制缓存总量。修改过的源文件
会产生新键，旧缓存不会被错误复用。

## 错误处理

加载状态为：元数据、预览、高清瓦片。高清瓦片失败时保留预览，仅显示非阻塞提示；只有
元数据和预览都失败才进入完整错误状态。错误类别区分格式不支持、文件损坏、资源限制、
取消、插件不可用和缓存写入失败。插件退出不会带走 Lumia 主进程，当前任务可以重试。

## 验证

- 单元测试覆盖阈值、受检尺寸计算、瓦片坐标、可见集合、缓存键、LRU 和 generation 取消。
- 格式测试覆盖 PNG、JPEG、WebP、BMP、TIFF、GIF 的普通样本和超大尺寸样本。
- 并发测试覆盖快速缩放、拖动和切图，确保旧结果不会覆盖当前图片。
- 使用 34752×11584、188 MB 的用户样本进行集成验证：能快速出现预览，放大后逐步变清晰，
  UI 不冻结，主进程与插件进程内存保持在预算边界附近。
- 最终运行 `cargo fmt --check`、`cargo check --workspace --all-targets`、
  `cargo test --workspace`，并启动 `cargo run -p lumia-app` 进行实际查看。

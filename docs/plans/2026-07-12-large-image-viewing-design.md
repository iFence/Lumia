# Lumia 超大图渐进式查看设计

## 背景

Lumia 当前把普通栅格文件路径直接交给 GPUI 解码并创建单张纹理。34752×11584
的 RGBA8 图片展开后约需 1.5 GiB，单边尺寸也超过常见 GPU 纹理限制，因此文件即使
只有 188 MB，也可能无法显示。

目标是在不影响普通图片快速路径的前提下，让 PNG、JPEG、WebP、BMP、TIFF、GIF
等常见格式的超大图片先显示有界预览，再按视口补充高清瓦片。按产品要求，全部逻辑
运行在 Lumia 主进程内，不使用插件或子进程，并坚持现有纯 Rust 解码体系。

## 组件边界

- `lumia-core` 保存 UI 无关的超大图判定、受检尺寸、瓦片几何、预览解码和磁盘栅格缓存。
- `lumia-app` 保存 GPUI 后台任务、generation 取消、优先级、LRU 和瓦片合成。
- 普通图片继续由 GPUI 按路径加载；只有超过阈值的图片才初始化超大图路径。
- 不扩展 `lumia-plugin-api`，不启动新的官方插件。

这是对 ADR 0001 中重型图像处理默认进入插件边界的窄化例外。例外只复用已经锁定的
纯 Rust 常见格式 codec，不引入 RAW、HDR、AI、网络或批处理能力。

## 超大图判定

读取元数据后，满足任一条件即进入 `LargeImageSession`：

- 任一边超过 8192 像素；
- `width × height × 4` 的受检结果超过 256 MiB；
- 图片尺寸超过应用定义的 GPU 安全纹理边界。

所有像素数、行大小、缓存长度和瓦片数量都使用受检运算，在任何分配或文件扩展前拒绝
溢出和不合理尺寸。

## 解码策略

首屏目标是最长边不超过 2048 的 BGRA8 预览。PNG 使用 `png` 的逐行接口，在顺序解压
过程中直接采样到预览，不创建完整帧。BMP 使用区域读取；TIFF 使用 chunk/strip；GIF
使用低层流式接口并只处理首帧。

当前 JPEG 和 WebP codec 只公开完整输出。它们把输出写入临时文件的内存映射，而不是
在 Rust 堆上创建数 GiB 的 `Vec`。完成后从映射分块生成预览和瓦片。开始前检查受检文件
长度和可用磁盘空间；空间不足时返回明确错误。

PNG 等顺序格式先完成一次低分辨率扫描并立即显示预览，随后在低优先级任务中再次扫描，
生成磁盘后备栅格。后备栅格采用固定 BGRA8 行布局，使所有格式共享同一瓦片读取路径。

## 数据流与渲染

加载顺序为：元数据 → 预览 → 后备栅格 → 可见瓦片。`LargeImageSession` 保存源文件标识、
原始尺寸、generation、预览、可见瓦片和请求状态。视口变化时，纯几何函数计算当前缩放
级别需要的 512×512 瓦片；GPUI 以预览为底图，将已就绪瓦片按原图坐标覆盖。

缩放、拖动和切图会使旧请求失效。无法中断的 codec 调用可以继续结束，但其结果必须通过
generation 检查后才能进入 UI。

## 并发与资源预算

流式主解码按格式要求顺序执行。独立瓦片的缩放、颜色转换和缓存读取可以并行，最大并发为
`max(1, min(available_parallelism - 1, 6))`。优先级为首屏预览、可见瓦片、邻近预取。

在途像素缓冲总量约束为 256 MiB，应用侧已准备纹理使用约 256 MiB LRU。磁盘缓存按文件
路径、大小和修改时间生成键，并设置总量上限。缓存使用 `.part` 写入和原子重命名；启动时
清理残缺或过期条目。

## 错误处理

高清瓦片失败时保留预览并显示非阻塞提示。只有元数据或预览失败时才显示完整错误状态。
错误区分文件损坏、格式不支持、尺寸溢出、内存预算、磁盘空间、取消和缓存 I/O。主进程内
解码失去插件崩溃隔离，因此所有 codec 输入前都启用尺寸限制，并避免在 UI 线程调用解码器。

## 验证

- 单元测试覆盖阈值、受检长度、瓦片坐标、可见集合、缓存键、LRU 和 generation。
- 格式测试覆盖 PNG、JPEG、WebP、BMP、TIFF、GIF 的普通样本和超大尺寸构造样本。
- 并发测试覆盖快速缩放、拖动和切图，确保旧结果不会覆盖当前图片。
- 使用用户提供的 34752×11584、188 MB PNG 验证预览、高清瓦片、响应性和内存边界。
- 最终运行 `cargo fmt --check`、`cargo check --workspace --all-targets`、
  `cargo test --workspace`，并用 `cargo run -p lumia-app` 实际查看。

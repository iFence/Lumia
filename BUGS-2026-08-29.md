# Lumia Bug Report — 2026-08-29

Scope: functional logic bugs. Distinct from `AUDIT-2026-08-29.md` (architecture)
and `AUDIT-2026-08-29-SUPPLY-CHAIN.md` (dependencies/CI).

Baseline: commit `2f1afd7` + working tree. All four bugs below are in the
comparison feature — the newest, least-reviewed code (untracked files).

Severity counts: **0 critical · 4 functional bugs** (1 high, 3 medium).

> **Status 2026-08-29 — all four fixed.** Verified with `cargo fmt --check`
> (clean), `cargo clippy --workspace --all-targets` (0 errors), and
> `cargo test --workspace` (254 passed, 0 failed, 1 ignored — unchanged from

## B1 (High) — Rotating the right comparison pane silently does nothing

`crates/lumia-app/src/comparison_transform.rs:355-371` writes
`state.rotation_quarter_turns`, but **that field is never read anywhere**.

Every read of a rotation value in this feature is
`self.viewer.rotation_quarter_turns()` — the *main* viewer
(`comparison.rs:96,126`, `comparison_transform.rs:80,189`). A grep for
`\.rotation_quarter_turns` across both files returns only the two write sites
(`:360-361`, `:364-365`) and four reads of `self.viewer.…`, never `state.…`.

The right pane renders `state.image` raw (`comparison.rs:127,228`) — no rotation
is ever applied to it.

`compare_rotate` **is** wired to the UI (`viewer_actions.rs:343,356` and
`status_bar.rs:128,142`), so the input is accepted and then discarded:

| Target | Result |
|---|---|
| `Some(true)` — right pane | **Nothing happens at all**; only the counter is written |
| `None` — both panes | Left rotates, right does not → **panes visibly desync** |
| `Some(false)` — left pane | Works correctly |

**Fix:** apply `lumia_core::rotate_decoded_image` (or `rotate_bgra8`) to
`state.image` using `state.rotation_quarter_turns` at render time, mirroring how
`load_state::display_image` handles the main viewer. The core helper is verified
correct — `raster.rs:192-196` swaps width/height for odd quarter turns and the
`turns => 1/2/3` index math at `:201-203` is right. Alternatively, remove the
field and disable rotation while the right pane is targeted.

**Resolution:** mirrored the main viewer's pattern instead of rotating per
frame. `ComparisonState` gained a private `rotated_image` cache and a
`display_image()` accessor that returns the rotated copy while a rotation is
active; `rebuild_rotated_image()` regenerates it with `rotate_bgra8` after each
rotation *and* after the async decode lands, so a rotation requested before the
image finished loading now applies. All five display sites (two in
`comparison.rs`, two in `comparison_transform.rs`, one in
`display_resample.rs`) read through `display_image()`, so frame geometry and
resample keys derive from the same bitmap that is actually drawn.

## B2 (Medium) — Left comparison pane's resample is sized from the wrong viewport

`crates/lumia-app/src/display_resample.rs:204,206`:

```rust
Some(state) => (
    state.left_pane_bounds,
    state.viewport,        // left_viewport  <- should be *self.viewer.viewport()
    state.right_pane_bounds,
    state.viewport,        // right_viewport
    ...
```

Both siblings are `state.viewport`. The renderer uses a different viewport for
the left pane — `comparison.rs:128`:

```rust
let left_viewport = self.viewer.viewport();
let right_viewport = &state.viewport;
```

So the resample *request* is built from `state.viewport` while `ready()` is
matched against a *key* built from `self.viewer.viewport()`
(`comparison.rs:136`). `ResamplePreview::ready()` requires exact key equality
(`display_resample.rs:58-62`), so when the two viewports differ the left pane's
resample **never matches**. The renderer then falls back to
`state.left_resample.latest()` (`comparison.rs:233`) — a bitmap rendered at a
stale scale — or to the raw source.

The trigger is common, not exotic:
- `self.viewer.viewport()` carries whatever zoom/pan the user had *before*
  entering comparison; `state.viewport` starts at `ViewportState::default()`.
  They diverge immediately.
- They also diverge whenever the two images have different dimensions under
  FitToWindow, since `pane_fit_scale` yields a different scale per pane.

**Symptom:** with a non-default resample filter selected, the left pane renders
blurry or at the wrong scale, or the filter silently appears not to apply to it.

**Fix:** capture the main viewport before the match — `ViewportState` is `Copy`,
so `let main_viewport = *self.viewer.viewport();` works — and use it for
`left_viewport`.

**Resolution:** done exactly that in `schedule_viewer_resamples`. `main_viewport`
is snapshotted immediately before the `match self.comparison.as_ref()` and used
for the `left_viewport` tuple element; `right_viewport` still uses
`state.viewport`. The resample request key now matches the key the renderer
builds at `comparison.rs:136`, so `ready()` hits and the left pane stops falling
back to a stale bitmap.

## B3 (Medium) — Cursor-anchored zoom desyncs the two panes

`crates/lumia-app/src/comparison_transform.rs:204,209` — the same copy/paste
pattern as B2:

```rust
Some(state) => (
    state.individual_target,
    state.left_pane_bounds,
    state.left_image_bounds,
    state.viewport,        // left_pre  <- should be *self.viewer.viewport()
    state.right_pane_bounds,
    state.right_image_bounds,
    state.image.as_ref().map(PreparedImage::dimensions),
    state.viewport,        // right_pre
),
```

`left_pre` should snapshot the *main* viewport (the left pane renders with
`self.viewer.viewport()`), but duplicates `state.viewport`. `right_pre` is
correct by coincidence.

The consequence is at `:318-333`:

```rust
let (pre_pan_x, pre_pan_y) = if target_right {
    (right_pre.pan_x, right_pre.pan_y)
} else {
    (left_pre.pan_x, left_pre.pan_y)      // wrong baseline when !target_right
};
let dx = pan_x - pre_pan_x;
let dy = pan_y - pre_pan_y;
if target_right { ... } else {
    self.viewer.viewport_mut().set_pan(pan_x, pan_y);
    state.viewport.pan_by(dx, dy);        // shifted by a bogus delta
}
```

When zooming with the cursor over the **left** pane, the partner (right) pane is
shifted by a delta derived from the right pane's *own* pre-zoom pan instead of
the left's — producing exactly the misalignment the comment at `:323-324`
("Shift the partner viewport by the same delta so paired images keep their
alignment") exists to prevent.

**Symptom:** scroll-wheel zoom over the left pane makes the right pane jump.

**Fix:** `left_pre` must be `*self.viewer.viewport()`.

**Resolution:** done in `compare_scroll_zoom`. `main_viewport` is snapshotted
before the tuple destructuring (at the same point as the pre-zoom pan baseline
is read, i.e. before `prepare_for_step` and the zoom mutation) and used for
`left_pre`. Zooming over the left pane now shifts the right pane by the left
pane's own pan delta, which is what the alignment comment at `:323-324` intends.

## B4 (Medium) — Zoom in/out is not wired up in comparison mode

`comparison_transform.rs:142-148` defines `compare_zoom_in` and
`compare_zoom_out`, which have **no call sites anywhere in the crate** — a grep
across `crates/lumia-app/src` returns only the two definitions.

Everything else in the module *is* wired, which makes the omission stand out:

| Handler | Wired at |
|---|---|
| `compare_scroll_zoom` | `render.rs:156-163` |
| `compare_pan` | `render.rs:249` |
| `compare_rotate` | `viewer_actions.rs:343,356`; `status_bar.rs:128,142` |
| `compare_toggle_fit` | `status_bar.rs:175` |
| `toggle_comparison_target` / `close_comparison` | `render.rs:46-47` (actions) |
| **`compare_zoom_in` / `compare_zoom_out`** | **nowhere** |

**Symptom:** keyboard and menu zoom do nothing in comparison mode; the only ways
to zoom are the scroll wheel and the fit toggle.

This is the same dead code flagged as M5 in the architecture audit — listed here
because it is also a user-visible functional gap, not just untidiness.

**Resolution:** wired at the two shared entry points, `zoom_in_view` and
`zoom_out_view` in `viewer_actions.rs`, which branch to `compare_zoom_in` /
`compare_zoom_out` when `comparison_active()`. Routing there rather than at the
action handlers means both the `ZoomIn`/`ZoomOut` keybindings *and* the
status-bar +/- buttons now work, matching how `compare_toggle_fit` is already
dispatched at `status_bar.rs:174`. `show_zoom_menu` is cleared before the branch
so the menu closes in both modes. The two dead-code warnings for these handlers
are gone (`lumia-app` went from 8 warnings to 7 before the unrelated import
cleanup).

## Note on the pattern

B2 and B3 are the same defect: a tuple destructured from `self.comparison` where
two adjacent elements that should differ were both written as `state.viewport`.
Because `ViewportState` is `Copy` (`lumia-core/src/viewport.rs:3`), the compiler
has no way to catch it — it is a silent logic error, not a type error. Worth
grepping for the same shape if comparison mode is extended further.

# Round 2 — defects found by running the installed build

After B1–B4 were shipped, a manual pass surfaced three more. Two are
comparison-mode regressions exposed by the fact that rotation now actually
works; one is a main-viewer navigation defect that was always there.

> **Status 2026-08-29 — all three fixed.** Verified with `cargo fmt --check`
> (clean), `cargo clippy --workspace --all-targets` (0 errors, no new lints),
> and `cargo test --workspace` (258 passed, 0 failed, 1 ignored — 254 baseline
> plus 4 new tests).

## B5 (High) — Rotating in comparison mode blanks the left pane

**Symptom:** rotating with the left pane targeted (or both) makes the left pane
show "Loading image…" instead of the rotated image.

**Cause:** `compare_rotate` (`comparison_transform.rs`) bumped
`self.viewer.rotation_quarter_turns` and then stopped. The left pane renders
through `self.loads.display_image(quarter_turns)`
(`comparison.rs:163`), which returns `self.rotated_image` for a non-zero
rotation — and nothing ever built it. The renderer fell through to the
`is_decoding()` placeholder at `render.rs:306-312`.

The main viewer's own `rotate_display` (`viewer_actions.rs:388`) does the
missing step: it calls `rebuild_rotated_image(Some(window), cx)` and
`refresh_large_image_tiles(window, cx)`. `compare_rotate` was written against
the pre-B1 code path, where the left pane's rotation came straight from the
viewer and no rotated bitmap was consulted.

**Resolution:** `compare_rotate` now mirrors `rotate_display`'s full sequence
and takes `&mut Window` so it can refresh tiles. It computes
`affects_left` / `affects_right` from the target mode up front, rotates the main
viewer plus annotations, rebuilds the comparison pane's rotated bitmap, then
rebuilds the main viewer's rotated bitmap and refreshes tiles. All four call
sites were threaded (`viewer_actions.rs` ×2, `status_bar.rs` ×2).

## B6 (Medium) — Wheel zoom on a non-hovered pane uses absolute cursor coordinates

**Symptom:** with individual targeting on the right pane, scrolling while the
cursor sits over the *left* pane throws the right pane's image off-frame.

**Cause:** `compare_scroll_zoom` anchored on
`(cursor − target_pane_image_origin) / old_scale`. When the target is not the
pane under the cursor, `cursor` is a window coordinate far outside the target's
frame, so the derived anchor was a point outside the image and the resulting pan
was wildly wrong.

**Resolution:** the anchor is now a *relative* position. Three helpers were
added to `comparison_transform.rs`:

- `relative_position(offset, extent)` — clamped fraction of the frame.
- `anchored_pan(pre, dimensions, old_scale, new_scale, fraction)` — pan that
  holds the image point at `fraction` steady while the scale changes.
- `usable_scale(scale)` — finite and non-degenerate guard.

The fraction is read from the pane the cursor is actually **over**; when
individual targeting sends the zoom elsewhere, that fraction is applied to the
target pane's own frame. With the cursor off both panes it falls back to the
frame centre.

This is a strict generalisation of the old behaviour: when the hovered pane *is*
the target, holding the fraction steady relative to the pane centre is
algebraically identical to holding the cursor's point under the cursor, so
ordinary zoom is unchanged. The partner-pane delta shift for `None` targeting is
also untouched.

## B7 (Medium) — Navigating to the next image re-scales the outgoing one

**Symptom:** clicking next/prev makes the *current* image jump to a different
scale, and only after a short delay does the next image appear.

Two independent causes, both fixed:

**(a) The fit reset fired too early.** `ViewerSession::replace_document`
(`lumia-core/src/viewer.rs`) called `viewport.reset_fit()` synchronously. The
outgoing image stays on screen until the incoming one finishes decoding, so the
reset re-scaled and re-centred the image the user was still looking at —
discarding their zoom, pan, and fit mode before the new image existed.

`replace_document` now sets a `pending_fit_reset` flag instead, exposed as
`take_pending_fit_reset()` (consumed exactly once, so animation frames are
safe). `rotate_by` clears the flag because it performs its own reset; `clear`
resets it. The app applies it through two new `LumiaApp` helpers in
`viewer_files.rs` — `install_current_image` (the single choke point every decode
path now uses instead of `ImageLoadState::set_current_image`) and
`clear_displayed_images` — which call `apply_deferred_viewport_reset`.

**(b) The stale resample bitmap crossed the document boundary.**
`ResamplePreview::latest()` returned the last finished bitmap regardless of
which file it came from. After a navigation, the outgoing image's filtered
bitmap was rendered into the incoming image's frame (letterboxed by
`ObjectFit::Contain`) until the debounced resample job caught up — which reads
as the old image jumping to a new scale.

`latest()` was replaced by `latest_for(path)`, backed by a new `ready_key`
field that records the key the cached bitmap was actually produced for
(distinct from `key`, which is overwritten as soon as a new job is scheduled).
A bitmap is only reused as a stopgap while it belongs to the same document. All
three call sites updated — main viewer plus both comparison panes.

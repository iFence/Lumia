# Lumia Codebase Audit — 2026-08-29

Scope: full workspace audit against the rules declared in `AGENTS.md`.
Commit audited: `2f1afd7` (master), with uncommitted working-tree changes present.

## Executive summary

The codebase is in **good health**. The declared architecture holds, the plugin
sandbox is genuinely well engineered, and the verification gate passes cleanly:
`cargo fmt --check` clean, `cargo clippy` 0 errors, **254 tests passing**, and a
hard 500-line module limit enforced by an automated architecture test.

The dominant risk is **not** code quality — it is **governance drift**. The app
has quietly grown a networking stack and ~3,000 lines of plugin-domain logic that
`AGENTS.md` explicitly forbids, with no ADR justifying either. The rules are
sound; they are just no longer being followed or kept up to date.

Severity counts: **0 critical · 4 high · 7 medium · 4 low**.

## HIGH

### H1 — Networking in `lumia-app` violates an explicit architecture rule, with no ADR

`AGENTS.md:78` states: *"Do not add heavy decoder, AI, networking,
batch-processing, or model SDK dependencies to `lumia-app`."* This is violated.

`crates/lumia-app/Cargo.toml:20-21,36` declares `http_client`, `reqwest_client`,
`url`. The client is constructed **unconditionally at startup** and installed
globally (`crates/lumia-app/src/bootstrap.rs:37-39`).

Four call sites:

| Location | Target | Auto-fires? |
|---|---|---|
| `update_check.rs:13` | GitHub releases API | yes, if `check_updates_on_startup` |
| `update_check.rs:21` | Changelog from GitHub raw | yes, same gate |
| `community_plugins.rs:24` | Community plugin index | **yes, unconditionally** |
| `viewer_actions.rs:415` | Arbitrary user-supplied URL | user action |

`bootstrap.rs:60,65` fires two of these on every launch.

**No ADR exists.** `docs/` contains a single file (the plugin signing guide),
which *references* `docs/adr/0006-…` and `docs/adr/0007-…` at lines 678-679 —
but the `docs/adr/` directory is not in the repository. Per `AGENTS.md:105`,
"any dependency policy change or major upgrade must include an ADR". The ADRs
that would justify this architecture change are missing.

**Mitigating:** all four calls are `cx.spawn(...).detach()`, so the UI thread
never blocks on them. The core image decode path (`image_loading.rs:252,380,416`)
is purely local and never touches the network. The community browser seeds from
a disk cache so it renders offline. The blast radius is therefore contained —
this is a governance failure, not a performance one.

**Remediation**
1. Write `docs/adr/0008-networking-in-lumia-app.md` recording the decision, or
   reverse it by extracting the stack into a leaf crate `crates/lumia-net` behind
   a cargo feature, so `lumia-app` no longer links a network stack by default.
2. Add a user setting for the community-index fetch (see H2/H4).

### H2 — Update installer is downloaded and executed with no integrity verification

`crates/lumia-app/src/update_check.rs:346-429`. `download_and_install` fetches
the release asset, then at line 415 executes it:

```rust
let _ = crate::shell::open_url_in_browser(&dest.to_string_lossy());
```

The **only** integrity check is a byte-count comparison at lines 400-404:

```rust
if let Some(expected) = total_bytes {
    if downloaded != expected { anyhow::bail!("download incomplete: ..."); }
}
```

`total_bytes` comes from `asset.size`, which is parsed from **the same HTTP
response** as the download itself. A size mismatch is therefore not an integrity
check at all — any attacker who can influence the response controls both numbers.

This is a self-update path that executes a downloaded binary. The project
**already has** Ed25519 verification infrastructure (`plugin_package.rs:171-182`,
plus `scripts/sign-plugin-package.mjs`); it is simply not applied here.

**Remediation:** publish a detached `.sig` for each release artifact and verify it
with the existing Ed25519 public key before executing. Fail closed.

### H3 — `download_image` has no size cap and no timeout

`crates/lumia-app/src/viewer_actions.rs:415-431` writes a user-supplied URL
straight to `std::env::temp_dir()`. This is the **only** download path in the app
without a size limit, which is inconsistent with the care taken elsewhere:
`community_plugins.rs:314` correctly enforces `MAX_PACKAGE_DOWNLOAD_BYTES`
(128 MiB) and `MAX_COMMUNITY_INDEX_BYTES` (4 MiB).

Compounding this, **no HTTP request in the app has a read timeout.** Zed's
`HttpClient::get` exposes no timeout parameter, and `reqwest_client` sets only
`connect_timeout(10s)` — a stalled read hangs the detached task indefinitely.

**Remediation:** apply the existing 128 MiB cap to `download_image`, and add an
explicit read timeout to all four request sites.

### H4 — Community index fetch is unconditional and cannot be disabled

`bootstrap.rs:65` calls `app.load_community_index(false, cx)` on **every startup**.
Unlike the update check, there is no `check_updates_on_startup`-style setting
anywhere in the codebase gating it. The update check is at least opt-out
(`settings.rs:61`, defaulting to `true`); this one is not configurable at all.

**Remediation:** add a `load_community_index_on_startup` setting. Given this is a
third-party plugin directory rather than a core feature, consider defaulting it
to `false`.

## MEDIUM

### M1 — ~3,000 lines of plugin-domain logic accreted into the UI crate

`AGENTS.md:76`: *"Keep UI code in `crates/lumia-app` thin."* Roughly 3,000 lines
of plugin *domain* logic live in the app crate rather than in
`lumia-plugin-host`:

`plugin_package.rs` 470 · `plugin_catalog.rs` 456 · `plugin_state.rs` 420 ·
`plugin_controls.rs` 417 · `plugin_management.rs` 408 · `settings_plugins.rs` 378
· `plugin_installation.rs` 267 · `settings_installed_plugins.rs` 321

The dependency evidence confirms the misplacement: `zip`, `sha2`, `ring`,
`base64`, and `semver` are all declared on `lumia-app`, yet they exist purely for
plugin package handling — while `lumia-plugin-host/Cargo.toml` carries only four
dependencies and no `zip`.

This matters beyond tidiness: `plugin_package.rs` is the **security-critical**
signature-verification and archive-extraction path (see "Clean" below — it is
well implemented). Security-critical code should sit behind a crate boundary
where it can be reviewed, tested, and audited independently, not embedded in the
20k-line UI crate.

**Remediation:** move the `plugin_package*` / `plugin_installation` /
`plugin_catalog` modules and their `zip`/`sha2`/`ring`/`base64`/`semver`
dependencies into `lumia-plugin-host`. Keep only presentation
(`settings_plugins.rs`, `settings_installed_plugins.rs`, `plugin_panel.rs`) in the app.

### M2 — `AGENTS.md` is materially stale

The documented structure no longer matches reality:

- **Crate graph** (lines 61-67) omits `lumia-setup` and `lumia-svg-thumbnail`.
- **Plugins** (lines 56-57) document only `lumia-plugin-sample`; five real
  plugins (raw, photoshop, jpeg-xl, jpeg2000, annotation) are undocumented.
- **Module list** (lines 36-53) names ~28 app modules; there are **80**.

Two of these are not merely cosmetic. `lumia-svg-thumbnail` ships a full SVG
rasterizer (`resvg`/`usvg`) as an **in-process COM server loaded into
`explorer.exe`** — a crash-isolation and supply-chain surface that `AGENTS.md:7`
("crash isolation") implicitly governs, yet it is entirely undocumented. Its
`Cargo.toml:15-17` pins `resvg` 0.46 specifically to reuse gpui's copy — a
fragile coupling that silently forks into two crates if gpui bumps.

`lumia-setup` performs **machine-wide uninstalls of legacy products**
(`setup.rs:14-21`) — privileged, destructive, undocumented.

**Remediation:** add an "Auxiliary Crates" section covering both, noting their
platform gating, that neither may depend on workspace crates, and the `resvg`
pinning constraint.

### M3 — `main.rs` is no longer a thin skeleton

`AGENTS.md:92`: *"`main.rs` … should be a thin skeleton: `mod` declarations,
constants, `actions!` macro, and `main()` — no business logic."*

`crates/lumia-app/src/main.rs` is 246 lines and defines three business-logic
functions: `ensure_file_associations_on_first_launch` (:164),
`ensure_svg_thumbnail_handler` (:186), and `log_windows_error` (:214). The file
also carries ~25 layout constants that arguably belong in `palette.rs`.

**Remediation:** move the three Windows first-launch helpers into
`shell/windows.rs` or a new `first_launch.rs`; move layout constants to `palette.rs`.

### M4 — `PluginPermission::Network` is declared but never enforced

`AGENTS.md:84`: *"Plugin permissions must be declared in the manifest and
enforced by the host."*

`PluginPermission::Network` exists at `lumia-plugin-api/src/manifest.rs:51`, but
the **only** enforcement site is `process.rs:296-302`, which checks just
`ReadInputPath` and `WriteTemporaryOutput`. Nothing references `Network` except a
UI label at `settings_installed_plugins.rs:306`.

Today this is latent rather than exploitable — the host passes only paths over
stdio and grants plugins no network handle. But a plugin runs as a **separate
process**, so it can open its own sockets regardless of what the manifest
declares. The permission is therefore decorative: it cannot be enforced at the
host level by construction.

**Remediation:** either remove the variant until real enforcement (an OS-level
sandbox or a proxy) exists, or document clearly that plugin process isolation is
permissive and permissions are advisory. Do not leave a declared-but-unenforced
permission in a security-facing enum — it misleads both plugin authors and
reviewers.

### M6 — Format sniffing implemented in the UI layer

`viewer_actions.rs:447-457` performs magic-byte format detection in `lumia-app`:

```rust
b if b.starts_with(b"\x89PNG") => Some("png".into()),
b if b.starts_with(b"GIF87a") || b.starts_with(b"GIF89a") => Some("gif".into()),
```

plus `extension_from_url` (:433-445). Format identification is a core-domain
responsibility; `lumia-core` already owns `is_supported_image_extension`, which
this code calls at :440. This duplicates and splits the concern.

**Remediation:** move both functions into `lumia-core::image::formats`.

## Clean — what is working well

Worth stating explicitly, since these are the parts that are easy to regress.

**Architecture boundaries hold.** No dependency cycles. `lumia-core` and
`lumia-plugin-api` are genuine leaves with zero workspace dependencies.
`lumia-plugin-host` depends only on `lumia-plugin-api`. No plugin depends on
`lumia-core` or `lumia-app`; `lumia-app` is the sole integration point.

**`lumia-core` is UI-free.** Grepping for `gpui|Render|Window|Element` returns
only false positives from `FitToWindow`. The decode path correctly delegates:
`professional_preview.rs` spawns plugins and validates results but performs no
decoding; `large_image.rs`, `display_resample.rs`, and `annotation_export.rs` all
import their domain models from core.

**The plugin transport is well engineered** — better than most implementations of
this pattern:
- A dedicated reader thread with an mpsc channel means **no write-then-read
  deadlock** on a full pipe buffer (`process.rs:209-232`).
- Bounded line reads (`read_bounded_line`, :234-266) cap responses at 1 MiB and
  reject oversized lines with `InvalidData` rather than OOM-ing.
- Timeouts on every request: 5s control / 120s task (:22-23).
- `Drop` terminates the child (:188-192) and every error path calls
  `terminate()` — no orphaned processes.
- Protocol version and response-ID mismatches are both rejected (:141-151).

**Plugin package security is genuinely hardened** (`plugin_package.rs`):
- Ed25519 signature verification over the manifest, which itself carries per-file
  SHA-256 hashes — so payloads are transitively authenticated (:171-182).
- Zip-slip prevented: `validate_archive_path` (:391-426) rejects absolute paths,
  `\`, `:`, NUL, non-`Normal` components (so `..`), trailing dots/spaces, and
  Windows reserved names.
- Zip-bomb limits throughout: 128 MiB compressed, 512 MiB total, 256 MiB/file,
  512 files, 576 entries (:19-25).
- Symlinks and encrypted entries rejected (:258-263).
- Downgrade attacks blocked (:223-231).

**Engineering discipline is strong.** 254 tests including 7 *architecture guard
tests* (`crates/lumia-app/tests/architecture.rs`) that mechanically enforce the
500-line rule and verify every plugin is declared in every release package (WiX,
macOS installer, Linux installer, release workflow). That is a genuinely good
practice. i18n is cleanly split (`i18n.rs` keys + `i18n/text_en.rs` +
`i18n/text_zh.rs`), keeping each file well under the size limit.

## Recommended order of work

1. **H2** — add Ed25519 verification to the update path (security, self-update path).
2. **H3 / H4** — size-cap `download_image`, add HTTP timeouts, add a setting to
   disable the community fetch.
3. **H1** — write ADR 0008, or extract `lumia-net` behind a feature flag.
4. **M1** — move plugin domain logic into `lumia-plugin-host`.
5. **M2** — refresh `AGENTS.md` structure and document the auxiliary crates.
6. **M4** — resolve the unenforced `Network` permission.
7. **M3 / M5 / M6 / M7** — mechanical cleanup: `main.rs`, dead code, format
   sniffing, ignored test.

Nothing here is on fire. The two items to treat with real urgency are **H2**
(self-update executes unverified binaries) and **H1** (the architecture rules and
the code have diverged, which is how the other findings crept in).

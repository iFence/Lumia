# Lumia 官方插件签名与密钥管理指南

## 1. 文档目的

本文面向 Lumia 维护者和官方插件开发者，说明后续开发、打包和发布官方插件时，公钥、私钥、运行时签名、安装包签名以及 GitHub Actions Secret 应如何管理。

本文描述的是 Lumia 当前信任模型：

- 安装身份由 Ed25519 签名验证，官方允许列表由签名脚本在打包时强制（只允许 `lumia.annotation` 与 `lumia.raw`）；
- 所有官方插件暂时共用一套 Ed25519 发布密钥；
- Lumia 应用只保存公钥；
- 私钥只保存在受控的离线位置和 GitHub Actions Secret 中；
- 插件运行时清单和最终安装包分别签名；
- 第三方插件签名、插件独立密钥和证书链尚未开放。

当前官方原始公钥（更新于 2026-07-29）：

```text
6b88de1c86a73ae666d4a44b54e3046900ff24a085a2515ada36d2b15cc55417
```

公钥可以公开，私钥不得进入仓库、文档、聊天记录、构建日志或发布附件。

## 2. 核心概念

### 2.1 私钥

私钥用于生成 Ed25519 签名。当前工具接受 PKCS#8 PEM：

```text
-----BEGIN PRIVATE KEY-----
...
-----END PRIVATE KEY-----
```

私钥承担 Lumia 官方插件发布身份。一旦泄露，攻击者就可能制作能够通过 Lumia 验证的恶意插件包。

### 2.2 公钥

公钥用于验证签名，可以提交到仓库并嵌入 Lumia。项目中存在两种表示：

- Rust 中的 32 字节数组；
- Node.js 打包脚本中的 64 位十六进制字符串。

两种表示必须来自同一把 Ed25519 私钥，并且始终保持一致。

### 2.3 运行时签名

文件：

```text
lumia.plugin.sig
```

它是对 `lumia.plugin.json` **精确原始字节**的 Ed25519 签名，使用 Base64 文本保存。

运行时签名保护：

- 插件身份；
- 插件版本；
- 入口文件声明；
- 能力和权限声明；
- UI 贡献；
- 资源路径和资源摘要。

对 `lumia.plugin.json` 重新排版、修改换行、修改版本或更新资源摘要后，旧签名都会失效，必须重新签名。

### 2.4 安装包签名

文件：

```text
lumia.package.sig
```

它是对 `lumia.package.json` 精确原始字节的 Ed25519 签名。外层清单记录安装包中每个负载文件的路径、大小和 SHA-256，因此安装包签名还会保护：

- 插件可执行文件；
- `lumia.plugin.json`；
- `lumia.plugin.sig`；
- 插件资源；
- 其他声明的负载文件。

运行时签名与安装包签名不能相互替代：

```text
私钥
 ├── 签名 lumia.plugin.json
 │      └── 生成 lumia.plugin.sig
 │
 └── 签名 lumia.package.json
        └── 生成 lumia.package.sig
```

运行时签名通常随插件源码提交；安装包签名由 Release CI 在编译完成后生成，不提交到仓库。

## 3. 当前密钥在项目中的配置位置

### 3.1 Lumia 验签公钥

文件：

```text
crates/lumia-app/src/plugin_package.rs
```

常量：

```rust
pub(crate) const OFFICIAL_PLUGIN_PUBLIC_KEY: [u8; 32]
```

Lumia 使用它验证外层安装包签名和官方 UI 插件运行时清单签名。

### 3.2 Node.js 打包公钥

文件：

```text
scripts/sign-plugin-package.mjs
```

常量：

```javascript
const OFFICIAL_PUBLIC_KEY_HEX = "...";
```

打包脚本会从私钥派生公钥并与此值比较。这样可以防止 CI 误用另一把私钥生成无法被 Lumia 接受的插件包。

### 3.3 GitHub Actions 私钥

仓库级 Actions Secret：

```text
LUMIA_PLUGIN_SIGNING_KEY_PEM
```

Release 工作流通过以下方式将它注入签名步骤：

```yaml
env:
  LUMIA_PLUGIN_SIGNING_KEY_PEM: ${{ secrets.LUMIA_PLUGIN_SIGNING_KEY_PEM }}
```

不要将私钥配置为普通 Repository Variable。Variable 不适合保存敏感信息。

## 4. 密钥保管策略

当前阶段采用“一套官方发布密钥签署所有官方插件”。这样与 Lumia 当前单公钥验证实现一致，也便于管理。

建议至少保存两份私钥：

1. 日常受控签名副本；
2. 加密的离线恢复备份。

建议要求：

- 私钥目录位于仓库之外；
- 只允许发布负责人访问；
- 私钥文件不由网盘公开同步；
- 备份使用加密存储；
- GitHub Secret 使用同一私钥的 PKCS#8 PEM；
- 不在 CI 中打印环境变量；
- 不在命令行参数中直接传递私钥正文；
- 本地临时环境变量使用后立即删除；
- 定期确认备份可以恢复，但不要在生产仓库中演练泄露场景。

开发者编写插件不需要私钥。只有修改正式运行时清单、制作正式发布包或执行密钥轮换时才需要使用私钥。

## 5. 首次生成密钥对

后续只有在首次建立信任根或执行密钥轮换时才需要生成新密钥。不要为每次发布重新生成密钥。

使用 OpenSSL 生成 Ed25519 PKCS#8 私钥：

```powershell
$secretDirectory = "D:\Secure\LumiaSecrets"
$privateKey = Join-Path $secretDirectory "lumia-plugin-signing-key.pem"
$publicPem = Join-Path $secretDirectory "lumia-plugin-signing-public.pem"
$publicDer = Join-Path $secretDirectory "lumia-plugin-signing-public.der"

New-Item -ItemType Directory -Force -Path $secretDirectory | Out-Null

if (Test-Path -LiteralPath $privateKey) {
    throw "Refusing to overwrite an existing Lumia signing key"
}

openssl genpkey -algorithm ED25519 -out $privateKey
openssl pkey -in $privateKey -pubout -out $publicPem
openssl pkey -in $privateKey -pubout -outform DER -out $publicDer
```

提取 32 字节原始公钥：

```powershell
$derBytes = [System.IO.File]::ReadAllBytes($publicDer)
if ($derBytes.Length -ne 44) {
    throw "Unexpected Ed25519 SubjectPublicKeyInfo length"
}

$expectedPrefix = [Convert]::FromHexString("302a300506032b6570032100")
for ($index = 0; $index -lt $expectedPrefix.Length; $index++) {
    if ($derBytes[$index] -ne $expectedPrefix[$index]) {
        throw "The public key is not an Ed25519 SubjectPublicKeyInfo value"
    }
}

$rawPublicKey = $derBytes[12..43]
$publicKeyHex = [Convert]::ToHexString($rawPublicKey).ToLowerInvariant()
$rustBytes = ($rawPublicKey | ForEach-Object {
    "0x{0:x2}" -f $_
}) -join ", "

Write-Output "Public key hex: $publicKeyHex"
Write-Output "Rust bytes: $rustBytes"
```

随后：

1. 将 `$rustBytes` 写入 `OFFICIAL_PLUGIN_PUBLIC_KEY`；
2. 将 `$publicKeyHex` 写入 `OFFICIAL_PUBLIC_KEY_HEX`；
3. 使用新私钥重新签署所有官方插件的 `lumia.plugin.json`；
4. 更新 GitHub Actions Secret；
5. 验证后发布包含新公钥的 Lumia 版本。

## 6. 开发新的官方插件

### 6.1 创建插件目录

推荐结构：

```text
plugins/
  lumia-plugin-<name>/
    Cargo.toml
    src/
    lumia.plugin.json
    lumia.plugin.sig
    assets/
```

插件 ID 使用稳定命名：

```text
lumia.<name>
```

插件发布后不要随意修改 ID。ID 是允许列表、安装目录、更新判断和状态管理的主键。

### 6.2 定义运行时清单

`lumia.plugin.json` 至少声明：

- `id`；
- `name`；
- `version`；
- `entry`；
- `capabilities`；
- `permissions`；
- 支持的输入和输出；
- UI 贡献；
- 资源路径和 SHA-256。

权限遵循最小授权原则。新插件不应为了未来可能使用的功能提前申请网络、密钥或写入权限。

### 6.3 加入官方签名允许列表

当前允许列表位于签名脚本：

```text
scripts/sign-plugin-package.mjs
```

常量：

```javascript
const OFFICIAL_PLUGIN_IDS = new Set(["lumia.annotation", "lumia.raw"]);
```

只有经过代码审查并准备由 Lumia 官方负责发布的插件才能加入该列表。签名脚本只允许该列表内的插件 ID 被打包；Lumia 运行时只验证 Ed25519 签名，不再校验 ID 白名单。新增官方插件时，还需要在 `KNOWN_OFFICIAL_PLUGINS` 中补充它在社区插件索引里的名称、描述、标签、作者和仓库信息，以便在社区插件浏览器中可被搜索到。

### 6.4 签署运行时清单

每次正式修改 `lumia.plugin.json` 后，执行：

```powershell
$privateKey = "D:\Secure\LumiaSecrets\lumia-plugin-signing-key.pem"
$manifest = "plugins\lumia-plugin-<name>\lumia.plugin.json"
$signatureBinary = Join-Path $env:TEMP "lumia-plugin-manifest-signature.bin"
$signatureFile = "plugins\lumia-plugin-<name>\lumia.plugin.sig"

openssl pkeyutl `
    -sign `
    -rawin `
    -inkey $privateKey `
    -in $manifest `
    -out $signatureBinary

$signatureBase64 = [Convert]::ToBase64String(
    [System.IO.File]::ReadAllBytes($signatureBinary)
)

[System.IO.File]::WriteAllText(
    (Join-Path (Resolve-Path ".") $signatureFile),
    "$signatureBase64`n",
    [System.Text.UTF8Encoding]::new($false)
)

Remove-Item -LiteralPath $signatureBinary
```

提交 `lumia.plugin.sig`，但绝不提交私钥或临时二进制签名文件。

### 6.5 为新插件建立打包流程

当前文件：

```text
scripts/sign-plugin-package.mjs
scripts/package-annotation-plugin.ps1
scripts/package-annotation-plugin.sh
```

仍包含 Annotation 专用的插件 ID、安装目录和文件名。开发第二个官方插件时，必须选择以下方案之一：

1. 将签名脚本改造为从命令行接收插件 ID 和安装目录；
2. 为新插件建立独立的、经过测试的打包脚本。

推荐优先将公共签名逻辑参数化，避免为每个插件复制密码学实现。参数化后仍需校验：

- 命令行插件 ID 与 `lumia.plugin.json` 一致；
- 安装目录符合安全命名规则；
- 插件 ID 位于官方允许列表；
- 入口文件和所有资源都被外层清单覆盖；
- 公钥与私钥匹配。

不要简单复制 Annotation 脚本后只修改输出文件名。当前 `INSTALL_DIRECTORY` 和插件 ID 校验如果没有同步修改，会生成错误包或在签名阶段失败。

## 7. 日常发布流程

一个官方插件的发布顺序应固定为：

```text
修改插件代码或清单
        ↓
更新资源 SHA-256
        ↓
使用官方私钥重新签署 lumia.plugin.json
        ↓
提交 lumia.plugin.json 和 lumia.plugin.sig
        ↓
Release CI 编译平台可执行文件
        ↓
CI 生成 lumia.package.json
        ↓
CI 使用 GitHub Secret 生成 lumia.package.sig
        ↓
CI 创建 .lumiaplugin（旧名 + 带版本号名）
        ↓
发布版 Lumia 验证最终安装包
        ↓
上传 GitHub Release
        ↓
update-community-index 任务重新生成社区插件索引
        ↓
推送到 awesome-lumia-plugin 仓库的 plugins.json
```

外层包必须按操作系统和架构分别生成。Windows、macOS 和 Linux 的可执行文件不同，不能共享同一个 `.lumiaplugin`。每个平台的打包脚本会额外产出一个带版本号且架构规范化的副本（例如 `Lumia-RAW-0.1.0-windows-x86_64.lumiaplugin`），社区插件索引使用它作为每个版本的固定下载地址，旧版本因此仍可安装，新版本会自动显示更新。

### 7.1 本地发布前验证

Windows 示例：

```powershell
$privateKey = "D:\Secure\LumiaSecrets\lumia-plugin-signing-key.pem"
$env:LUMIA_PLUGIN_SIGNING_KEY_PEM =
    Get-Content -Raw -LiteralPath $privateKey

try {
    cargo test -p lumia-app annotation_package_signature_and_assets_are_valid
    cargo build --release -p lumia-app
    .\scripts\package-annotation-plugin.ps1
    .\scripts\verify-plugin-package.ps1 `
        -Package "target\Lumia-Annotation-windows-x64.lumiaplugin"
}
finally {
    Remove-Item Env:\LUMIA_PLUGIN_SIGNING_KEY_PEM `
        -ErrorAction SilentlyContinue
}
```

不要将 `$env:LUMIA_PLUGIN_SIGNING_KEY_PEM` 写入 PowerShell Profile。

### 7.2 GitHub Secret 配置

签名私钥：

```powershell
Get-Content -Raw -LiteralPath $privateKey |
    gh secret set LUMIA_PLUGIN_SIGNING_KEY_PEM
```

索引同步令牌：

```text
LUMA_INDEX_ACCESS_TOKEN
```

这是一个仅对 `iFence/awesome-lumia-plugin` 仓库拥有 Contents 读写权限的
fine-grained Personal Access Token，用于把重新生成的 `plugins.json` 通过
Contents API 推送回去。它与签名私钥完全无关，也**不需要**对 `iFence/lumia`
仓库或整个组织授权。

```powershell
gh secret set LUMA_INDEX_ACCESS_TOKEN
```

该令牌是尽力而为的：缺失或无效时，`update-community-index` 任务只输出
warning，不会让发布失败——签名安装包已经上传到 Release，之后可以单独重跑该
任务补同步索引。

只检查 Secret 名称：

```powershell
gh secret list
```

GitHub 不允许读取已经保存的 Secret 值。需要更换私钥时，重新执行 `gh secret set` 覆盖即可。

如果使用 Organization Secret，必须明确授权 Lumia 仓库访问。当前 Release job 没有声明 GitHub Environment，因此不要只配置 Environment Secret，除非同时修改 job 的 `environment` 配置。

## 8. 哪些变更需要重新签名

| 变更 | 重新生成 `lumia.plugin.sig` | 重新生成 `lumia.package.sig` |
|---|---:|---:|
| 修改插件版本 | 是 | 是 |
| 修改入口文件名 | 是 | 是 |
| 修改能力或权限 | 是 | 是 |
| 修改 UI 贡献 | 是 | 是 |
| 修改资源摘要 | 是 | 是 |
| 修改插件可执行文件但清单不变 | 否 | 是 |
| 修改资源文件内容 | 先更新摘要，再重新签名 | 是 |
| 仅修改源码但产物完全不变 | 否 | 发布时仍重新生成 |
| 仅修改安装包目标平台 | 否 | 是 |

Release CI 每次都应重新生成外层签名。运行时签名只有在 `lumia.plugin.json` 精确字节发生变化时才需要重新生成，但发布前必须再次验证。

## 9. 密钥轮换

### 9.1 何时轮换

出现以下情况必须轮换：

- 私钥丢失且无法从安全备份恢复；
- 怀疑私钥被复制或泄露；
- 有权访问私钥的人员权限发生重大变化；
- 构建环境或 Secret 管理系统遭到入侵；
- 密钥管理策略要求定期轮换。

### 9.2 当前单公钥模型的轮换步骤

1. 停止官方插件发布；
2. 生成新 Ed25519 密钥对；
3. 更新 Rust 内嵌公钥；
4. 更新 Node.js 打包公钥；
5. 使用新私钥重新签署每个官方插件的 `lumia.plugin.json`；
6. 更新所有 `lumia.plugin.sig`；
7. 更新 GitHub Secret；
8. 运行全部签名和安装测试；
9. 发布包含新公钥的 Lumia；
10. 使用新版本 Lumia 验证新插件包；
11. 安全销毁不再需要的旧私钥副本。

仅更新 GitHub Secret 是不够的。新私钥必须与 Lumia 内嵌公钥以及签名脚本公钥一致，否则 CI 会报：

```text
signing key does not match Lumia's official plugin public key
```

### 9.3 旧包兼容性

当前 Lumia 只信任一把公钥。直接替换公钥后，新版本 Lumia 将不再接受由旧密钥签署的安装包。

如果未来已经存在大量公开发布的旧插件包，应先实现：

- 公钥 ID；
- 受信任公钥集合；
- 旧公钥撤销状态；
- 签名清单中的 `key_id`；
- 有时间边界的双公钥过渡期。

在没有实现公钥集合前，不要承诺密钥轮换后继续支持所有历史安装包。

## 10. 多插件密钥策略

### 当前推荐

官方插件数量较少时，继续使用一套发布密钥：

- 实现简单；
- 与当前单公钥验证一致；
- 只需维护一个 GitHub Secret；
- 所有官方插件使用相同发布流程。

### 何时改为每个插件独立密钥

满足以下任一条件时，应考虑按插件分钥：

- 插件由不同团队维护；
- 部分插件由外部合作方构建；
- 插件数量明显增加；
- 不同插件具有不同发布权限；
- 希望单个插件密钥泄露时不影响其他插件。

迁移前需要先设计：

```text
plugin_id → key_id → trusted public key
```

外层和运行时清单都应声明 `key_id`，Lumia 根据插件 ID 和 key ID 选择公钥。不能仅增加多个同名 GitHub Secret，而不修改 Lumia 验证协议。

更成熟的方案是离线根密钥签发插件级子密钥，但这涉及证书格式、吊销、有效期和根密钥离线流程，当前版本不应提前引入。

## 11. 常见错误

### `LUMIA_PLUGIN_SIGNING_KEY_PEM is not configured`

原因：

- 仓库 Secret 未创建；
- Secret 名称拼写错误；
- 只配置了 Environment Secret，但 job 没有关联该 Environment；
- Organization Secret 没有授权 Lumia 仓库；
- 工作流来自无法读取 Secret 的不受信任上下文。

处理：

```powershell
gh secret list
```

确认存在：

```text
LUMIA_PLUGIN_SIGNING_KEY_PEM
```

### `signing key does not match Lumia's official plugin public key`

原因：GitHub Secret 中的私钥与代码中的公钥不属于同一密钥对。

处理：

1. 从私钥重新派生公钥；
2. 对比 Rust 和 Node.js 中的公钥；
3. 不要通过反复生成新私钥碰运气；
4. 如确认需要换钥，执行完整密钥轮换。

### `plugin package signature is invalid`

可能原因：

- `lumia.package.json` 在签名后被修改；
- 使用了错误私钥；
- 签名文本损坏；
- 验证器仍包含旧公钥；
- CI 上传的不是刚刚验证的文件。

### 运行时清单签名失败

可能原因：

- 修改了 `lumia.plugin.json` 但没有重新签名；
- 文本编辑器改变了换行或编码；
- `lumia.plugin.sig` 来自另一把私钥；
- 打包脚本复制了旧签名。

签名验证针对精确字节。不要解析 JSON 后重新序列化再验签。

### 重新运行旧 tag 仍然失败

GitHub Actions 重跑使用原 tag 指向的原提交。如果密钥轮换修改尚未进入该提交，重跑仍然会使用旧公钥和旧签名。

推荐提交密钥轮换的公钥与签名变更，然后创建新版本 tag。不要为了修复签名而随意重写已经公开发布的 tag。
